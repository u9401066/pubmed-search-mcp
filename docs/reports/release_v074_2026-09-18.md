## Additional reproduced failures and fixes

| Trigger | Previous behavior | Repair and evidence |
| --- | --- | --- |
| Clients request different concurrency limits for one service | First caller's capacity silently wins | FIFO `ConcurrencyLimiter` only tightens; admitted work drains before further admission. Regression reproduced excess capacity, then passed; cancellation before/after reservation returns capacity exactly once |
| A 429 arrives as its caller's deadline expires | Cooldown update can be skipped with the expired budget | Atomic loop-local cooldown update is independent of that request's remaining time; a virtual-clock regression verifies the full 600-second cooldown |
| A cancelled Entrez thread is queued behind the runtime lock | The thread later sends the abandoned request | Propagate per-attempt cancellation through `to_thread` context and recheck after taking the lock; regressions cover function and EntrezBase entrypoints |
| An Entrez response arrives after cancellation | Its handle can be abandoned | Close the late handle before discarding the result; keep Entrez global configuration restoration in `finally` |
| A cancelled Entrez waiter receives a late 429 in its background thread | The vanished waiter cannot communicate Retry-After | Dispatch cooldown to the owning loop with `call_soon_threadsafe`; regressions cover a long header and a header-less 429 |

No request-rate quota was raised. NCBI retains one shared operation slot;
BaseAPIClient sources default to two. A lower configured capacity is never
raised by a later caller. Already admitted operations cannot be recalled;
shrinking a limit takes effect as they drain. Registries remain event-loop-local,
so multi-worker deployments need external quota coordination. An already sent
request or a running synchronous thread cannot be forcibly stopped.

The existing shared transport remains the single owner of rate and retry policy.
Entrez adds only the context required to carry cancellation and late responses
across its synchronous boundary. Pipeline scheduling stays in the application
layer and does not bypass provider admission.
